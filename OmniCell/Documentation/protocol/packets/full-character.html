The inventory entries end in a GameData::ACGItem_t, four int32s of which the type holds three - two templates and a level masked to 0x1FF - with the fourth written as a literal zero at 0x1000E9C3 and read into nothing at 0x1000EA01, so it is reserved rather than unknown. What blocks green is the rest. The int32 after the skill map is two flag bits, split at 0x10073E7B: bit 0 says the character is in a team and bit 1 that the team is in a raid, and when bit 0 is set an Identity follows, then either an int32 and six team objects or one team object and no int32 - the dispatcher writes that int32 to +0x38 of the team subsystem at 0x10074166 and pushes the six objects into it at 0x1007417C, six being what a raid is. Every captured copy has both bits clear, so none of it has ever been on the wire here and the model does not implement it. The two lists after the flags are the wrong element type for the same reason: 0x1002BA77 reads one Identity per entry, not four int32s, and 0x100A71AE reads a whole GameData::SpellData_t per entry through GameData's own stream operator - an empty list of the wrong type is byte for byte an empty list of the right one, and every captured copy leaves both empty. The research list has a second form as well: its element reader at 0x10052D9D takes an int32 that is either a plain id or a marker whose top twenty four bits are all set, and only the marker form carries the two further int32s this model always reads. The three twenty byte lists - skills, perks and nanos - are lock timers, and today's captures are what say so. All three carry the same record and all three go straight into their own subsystem through the same range-insert at 0x10074898, which divides by sixteen, so the version at the front is not kept in memory. Nothing in the client reads an entry back that could be found, so the two int32s are named from values rather than code. Seven entries are now captured across two of the lists. In the skill list the identity's type half is zero and its instance is a stat id - 123 firstaid, 140 mapnavigation and 566 gos - and the first int32 against each is 40, 60 and 600, which are the lock times those three skills have always had, the last being the ten minute Grid recharge. The nano list carries type 1, instance 527, and 180 four times over. Across all seven the first int32 is constant for a given id and the second is not, and the second is strictly less than the first every time - 17 and 12 under firstaid's 40, 372 under gos's 600, 3 under mapnavigation's 60, and 29, 86, 139 and 176 under the nanos' 180. So the first is how long the lock lasts and the second how much of it is left. This entry used to say no capture carried an entry in any of the three lists, which stopped being true on 2026-09-11. The team block went in on 2026-09-11 and the packet can be read in a team now. It could not be before: the block is gated on a flag that is zero unless the character is actually in one, no capture had ever had it set, and four FullCharacters from a two-account session that afternoon sat in the audit as an unreadable message id rather than as a decode failure. The reader at 0x10073E7B takes an int32 and splits bits 0 and 1; on bit 0 it reads the team's Identity, and then either an int32 and six team objects when bit 1 is also set, or one team object when it is not. A team object is an X3F1-counted list read by 0x101261AC, and each member is a 0x30 byte record read by 0x1012634F: an Identity, a counted string, an int32, a byte and two int16s. The captures name two of those. The first int16 is the level - it holds 5, 6 and 7 across four snapshots of two characters levelling together, rising over time and differing between the two at the same moment. The second is the profession: 14 for one and 8 for the other, constant while the level moved, and 14 is Keeper in this model's own enum against an account that is a Keeper. The other two, the int32 and the byte, are zero throughout. One limitation is worth stating in the model and here: the client extracts bits 0 and 1 and ignores the rest of the int32, while the conditionals key on the whole value being 1 or 3. That is exact for every value the client can tell apart, and would differ only for a bit the client itself ignores. Three of the list element types were checked against their readers on 2026-09-11 and two of them were wrong, in the way an always-empty list hides: an empty list of the wrong element type is byte for byte an empty list of the right one, so the round trip could never say so. Pets is one Identity an entry and was sixteen bytes; it is fixed. Buffs is a whole GameData::SpellData_t and is still four int32s, because that type is the entire spell format subsystem rather than a record - it is named here so that nobody reads the round trip as agreement. The research entries had a real second form, and that one could have bitten: the record is sixteen bytes when its first word is a 0xFFFFFF00 marker and twenty when it is a plain id, and reading the short form for the long one leaves an int32 on the wire and turns every entry after it into nonsense. Both forms are modelled now, which needed one new criterion, NotHasAll - the complement of HasAll, because the branch is on whether the top twenty four bits are all set and HasNone asks a different question. Buffs was fixed the same day. The obstacle was never the record - GameData::SpellData_t is NanoEffect, which this model has had all along and three other messages already carry lists of - it was that those three reach it through hand-written serializers for the whole message, so the type could not be named from a message described by attributes. Registering a serializer for the type itself is enough, because the array serializer resolves its element through the same registry. SpellList still reads its 6,809 effects across fourteen game functions, so nothing that already worked went near it.
