Native client proof: MessageProtocol.dll Message_t::CreateDataBlock creates bytes 2–15; Connection.dll Connection_t::Send at RVA 0x16F3 writes bytes 0–1, 4–7; N3.dll n3InfoItemRemote_t::Write at RVA 0x98F4 writes opcode, affected identity, and ToBePassedOn at bytes 16–28. Retail captures independently match those writes. Packet body: Every byte is read and all but one are named. This page did not exist until 2026-09-12 - the packet had a managed schema and no byte table - and the first cut of it, written the same day, was wrong twice and is worth saying so. It claimed no capture contains one; four do, each carrying five missions, and all four round trip byte for byte. And it left two rows open that the schema had already named, because the schema was not read first. Both names come from one error message, which the first pass had not found: at 0x1016BB20 the client prints "ERROR: invalid data for ACGQuestIIR_t %u:%u in stream: Difficulty = %u (valid is [%d, %d]) / Dimension values = %s / Seed = %u / Originator = %u:%u %u (valid is [%d, %d])" and the pushes at 0x100CA062 line those four names up with the fields the reader filled. So the int32 is a seed and the byte with the identity after it is an originator. Extracted-client QuestAlternativeIIR_t has vtable 0x1016C004, reader 0x100CB232, dispatcher 0x100CB181 and version 0x100CB4B4, and it derives from ACGQuestIIR_t, which is abstract - three of that base's slots are _purecall - so the base's own id is not a message and its page says so. The reader is two parts: 0x100CB24A calls the base reader at 0x100C9F49 for the first twenty one bytes, then a count and that many missions. It is the mission terminal, and it goes both ways, which is the one thing the first pass got right that nothing else had recorded. The client builds one of these itself: n3EngineClientAnarchy_t::N3Msg_GenerateMissions at 0x10016276 takes a MissionGenerateInfo_t, constructs a QuestAlternativeIIR_t at 0x100CB351 - which is where the name string at 0x1016BA64 comes from - fills in the difficulty, the six dimensions and the originator pair, and hands it to n3EngineClient_t::SendIIRToServer. The server answers with the same shape carrying up to five missions, and the dispatcher walks them into the list the mission window reads through N3InterfaceModule_t::N3Msg_GetMissionSelectionList; that window is the one that says "No missions available, please try again later!" when the list comes back empty. So a server has to accept this message as a request and answer it with the same id. Three further things GameData names rather than the captures. The six bytes are a GameData::DimensionValues_t, read one byte per dimension at 0x100022FD, and DimensionValues_t::GetDimensionName at 0x1000219B is a table of the six in wire order. They are signed: the operator adds a hundred to each and refuses anything over two hundred, which is why the captured 229 and 254 are in range - they are minus 27 and minus 2. The originator is a nine value enum and GetQuestOriginatorName at GameData.dll 0x10002D0A is a table of its names, with IsTeamOriginator at 0x10002D23 answering yes to the even ones, which pairs each booth with its team version; all four captures carry NeutralBooth. And the mission count is capped by the client's other complaint, 0x100CB27C: "ERROR: invalid data in QuestAlternativeIIR_t stream %u:%u: - Number of quests = %u", printed when it is above five. The mission record itself needs no work: it is the same 0xF8 byte quest record QuestFullUpdate carries, read by the same 0x100ABEA7, and that page walks it to the last instruction. The byte after each mission was the last thing outstanding and it is now a dead end rather than a question. It travels with its mission into the sixteen byte MissionData_t records the mission window reads, GUI.dll copies each record whole into a MissionListEntry_c, and from there nothing reads it: not the window, and not the one path that talks back to the server, since N3Msg_SelectMission carries only the mission's Identity out of the record. So every row here is proven and what keeps the packet amber is the same thing that keeps sixteen others amber - two of its fields are ones the client reads and drops. Across the four captures the five bytes read 0, 1, 2, then 3 or 6, then 6, 9 or 24, which is index-like at the front and is not an index at the back; recorded in case a capture of a terminal offering fewer than five ever separates them.
