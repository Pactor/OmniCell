Native client proof: MessageProtocol.dll Message_t::CreateDataBlock creates bytes 2–15; Connection.dll Connection_t::Send at RVA 0x16F3 writes bytes 0–1, 4–7; N3.dll n3InfoItemRemote_t::Write at RVA 0x98F4 writes opcode, affected identity, and ToBePassedOn at bytes 16–28. Retail captures independently match those writes. Packet body: No capture carries this message, so all of it comes from the client, and the client is unusually forthcoming about it. Extracted-client OrgClientIIR_c has vtable 0x101713EC, reader 0x101265FE and writer 0x1012653F, and the two are the same four fields in the same order: a byte, an Identity, an int32, and a tail chosen by the byte. The byte is the command, and the reader refuses anything outside 1 to 31 before reading another thing. The tail is a jump table - 0x10126698 for reading, 0x101265B4 for writing, the same twenty eight entries either way - with three arms: an argument string for thirteen commands, one byte for Promote alone, and nothing for the other fourteen. This model had the string arm nearly right and the byte arm not at all: it wrote a string for BankPaymembers, which takes the empty arm, and wrote nothing for Promote, which takes the byte. The int32 is not computed anywhere in the client. It is the first argument of the export N3Msg_TextCommand(int, const char*, const Identity&): the constructor at 0x101266B4 puts that parameter straight into the message at +0x24 and nothing else ever writes the field. GUI.dll supplies it, at all three of its call sites, from the chat window object's own member at +0x1EC - and the client's debug commands, N3Msg_DebugSpellListToChat and N3Msg_DebugCriteriaToChat, take the same leading int and hand it to the chat text listeners as the first argument of the dispatch at 0x10012B6E, which is how a command's output finds the window that asked for it. Commands raised by a dialog rather than typed pass zero: N3Msg_OrgPromotionConfirmed builds this message directly at 0x1001DD8C with no window to name, and a one in the Promote byte, where typing the same command at 0x10041093 passes the window and a zero. The jump table was read out entry by entry on 2026-09-11 rather than inferred, and it agrees with this model exactly. The byte table at 0x10126698 maps command less one to one of three arms whose addresses sit at 0x1012668C: a counted string at 0x10126656, one byte at 0x10126664, and nothing at 0x10126676. The thirteen that take a string are Create, StartVote, Vote, Kick, Tax, BankAdd, BankRemove, History, Objective, Description, Name, GoverningForm and StopVote; Promote alone takes the byte; the other fourteen take nothing. That is the same thirteen and the same one this model has. The one doubt this page used to carry is also settled: the reader accepts 1 to 31 but the table is guarded by cmp eax, 0x1B, so commands 29, 30 and 31 skip the tail entirely, and a model that reads nothing for a command it does not name is right about them by construction.
