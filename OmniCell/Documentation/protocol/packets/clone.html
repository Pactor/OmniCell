Retail captures independently match those writes. Packet body: Every byte is identified. Extracted-client CloneIIR_t vtable 0x10161EB8 identifies reader 0x10072E3B, writer 0x10072DDC and dispatcher 0x10072EB0; the reader and the writer emit the same six fields in the same order, so there are two independent sources for the layout. The dispatcher resolves the message identity to a SimpleChar_t and calls 0x10058800, which writes the four scalars straight into that character's stats - head mesh into 64, race into 89, breed into 4, sex into 59 - then hands the cloth list to the character's appearance at 0x100483E5 and sets name slot 3 from the string at 0x1005BB92. It reads monsterscale, stat 360, of its own accord, so scale is not carried here. The cloth record is GameData.dll's ClothData_t: reader 0xA661 for one entry, 0xA709 for the X3F1-counted list. 0x100483E5 indexes the appearance table with group * 5 + place, which is why a group is five places wide. The string carries no count at all - BinaryStream.dll 0x100013A7 reads bytes until it reads a zero and 0x100011F4 writes the characters and then a zero. No copy of this message appears in any capture, so CloneMatchesTheLayoutTakenFromTheClient pins the layout rather than checking it against retail; the two ints a cloth record carries only when its place has a positive high half have a known position and destination in the appearance table but no named gameplay meaning, and have never appeared on the wire.
