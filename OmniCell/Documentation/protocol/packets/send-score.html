Retail captures independently match those writes. Packet body: This is the battlestation scoreboard, and the first array is settled outright. Extracted-client SendScoreIIR_t has vtable 0x1017249C, dispatcher 0x10132085, reader 0x10132050 and writer 0x10131F61. Writer helper 0x10131F18 and reader helper 0x101321D1 prove two consecutive X3F1-counted arrays of int32s, each capped at 30,000 entries. The dispatcher copies both vectors onto the stack and emits GlobalSignals_c + 0x238 with the pair, and that was as far as this went: nothing in Gamecode subscribes. A signal scan finds the one subscriber, in GUI.dll at 0x100F91DE, handing the signal the handler at 0x100F8758, and that handler is in a window whose own name is in the strings a few hundred bytes further on - "Battlestation" at 0x100F8987 and "BattlestationConfig" at 0x100F8A82. The first array is named by what the handler does with two of its elements and nothing else. It wraps element 0 in <div align="center"> and hands it to the view named "ClanVP" at 0x100F889D, and does the same with element 1 into the one named "OmniVP" at 0x100F87D4. Both go through MSVCP100's operator<<(ostream&, int), so they are counts rather than ids. Neither read is guarded by the array's length, so the server always sends at least two and anything past the second is read by no one. The second array is one value per entry of a list the window already holds. The handler compares its length against the window's vector at +0xA8 and gives up when they differ, and otherwise walks the two together, handing entry i's value to the row object at index i. That row is built by the handler at 0x100F8637, which a signal scan places on GlobalSignals_c + 0x23C - a different message, whose dispatcher at Gamecode 0x1013104E also raises the "battlestation_window". The row stores the window's three-texture vector at its own +0x128, and the value from this array is used at 0x100F81A0 as an index into it: the window loads exactly three textures at 0x100F8AE4 through 0x100F8B31, GuiResourceManager_t::GetGuiTexture with ids 301, 303 and 302 in that order. So each value is a state in a set of three, per battlestation site, and which of the three means what is not in this module. That, and the elements past the second in the first array, are what keep this off green.
