Retail captures independently match those writes. Packet body: Every byte is identified, and one call names all five fields. Extracted-client ReloadIIR_t has vtable 0x10162280, reader 0x10076C2A, writer 0x10076C83 and dispatcher 0x10076CC9; the reader takes two Identities and three int32s and the writer emits the same five, so the layout has two sources. The dispatcher resolves the message identity to a character, takes the fight handler at character +0x1D4 - the member N3Msg_GetAttackingID, N3Msg_CanAttack and N3Msg_GetSpecialAttackWeaponName all work through - and hands it the five fields at 0x100697BD, which splits into two halves. The ammunition half works on the character's inventory. With the flag set it calls 0x10049391 with a slot of -1, ending at 0x1002AB07: fetch the entry, free it, clear the slot. With the flag clear it calls 0x10049354, ending at 0x1002AF06: fetch the entry at that slot and set its +2 - the count int16 every container record carries - to the int32, clamped to 0 through 0xFFFF, marking the entry changed if it moved. Either way the Identity both paths work from is an inventory location and not an item: each checks that its type lies between 0x65 and 0xF9, which is the range of inventory pages, and uses its instance as the slot. The weapon half resolves the second Identity to a WeaponItem_t - the cast target at 0x101BFCC8 says so - reads stat 0x1A, Energy, abandons the message if it comes back negative, and sets that stat to the second int32. The last field is an int32 on the wire and a boolean everywhere else: the reader keeps only whether it was non-zero and the writer puts that back as an int32, so anything other than 0 or 1 does not survive a round trip through the client and nothing should send it. No capture contains one, so ReloadMatchesTheLayoutTakenFromTheClient pins the layout rather than checking it against retail; before this the message had no C# at all.
