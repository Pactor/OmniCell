Retail captures independently match those writes. Packet body: No capture carries this message, so all of it is the client, and the client says it twice - the reader at Gamecode.dll 0x10075557 and the writer at 0x100755EA are the same four fields in the same order and with the same condition on them. The first int32 is a flag and not a count: zero and the message is an Identity and nothing else; one and it carries a stat table before the Identity and one more int32 after it. This model had read all four unconditionally, and had the last of them as a four byte string called Hash - the right width and nothing else, since the reader takes it with the same int32 reader it uses for the rest. The short form, which is what the client writes when there is no character to report, came out as rubbish and ran off the end. The constructor at 0x10075C91 says where the two halves come from: given a character it takes that character's stats and the identity of whatever is in their sixth inventory slot; given none it takes an Identity from its caller and no stats at all. The stat table is read by GameData's shared reader at 0x10009DAD, which takes a plain int32 count rather than the X3F1 count most lists on this wire use, and seeds any stat it is not told about with 1234567890. One field is left. The trailing int32 is the constructor's third argument, put at the message's +0x24 without being looked at, and nothing in the client calls that constructor - so where the value comes from is outside this module, and this message's dispatcher is the shared do-nothing at 0x100A0CE3, so nothing reads it back either. Corrected on 2026-09-11, and the correction is that this entry was reading the wrong dispatcher. It said the trailing int32 had no name because nothing calls the constructor that supplies it and this message's dispatcher is the shared do-nothing at 0x100A0CE3. MechInfoIIR_t's dispatcher is its own, at 0x10075646, and at 0x100756D3 it pushes the message's + 0x24 and then 0x296 into the character stat interface. 0x296 is 662, which this repository's own stat table calls mechdata. So the field is named by the receiving side after all.
