Three version checks, each abandoning the message on a mismatch: 11 against the static at 0x101C2160, 2 against 0x101C2084 opening the tail, 3 against 0x101C1F80 closing it. The two bytes are stat writes - 0x100A1B83 sign-extends the first into stat 55 inventoryid and 0x100A1B94 the second into stat 220 currbodylocation. The marker is the shared item-message constant; the client reads it and never reads it back. The position is present only when the owner identity's instance is zero, which is never the case in a captured chest. The trailing Identity list is named now too. It belongs to LockableItemFullUpdate, the class between this one and SimpleItemFullUpdate, and an identity in it may lock and unlock the item: the dispatcher at 0x100A0BEF adds every entry to the LockableItem_t's own list, and 0x10085890 walks that list comparing each entry against whatever is acting on the item, toggling the lock and printing Feedback_YouUnlockedTheItem or Feedback_YouLockedTheItem on a match. The 50 beside it is settled - it is read into **(message + 0x60) + 0x4AC, and that address resolves, because message + 0x60 is the stat table the message fills in, built at 0x10009D97 as a vector of 1,200 ints every one seeded with the 1234567890 unset sentinel and indexed by stat id directly. Byte offset 0x4AC is element 299, lockdifficulty, which is exactly what a container has and 50 is exactly what one looks like.
