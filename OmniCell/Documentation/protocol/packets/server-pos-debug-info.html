Native client proof: MessageProtocol.dll Message_t::CreateDataBlock creates bytes 2–15; Connection.dll Connection_t::Send at RVA 0x16F3 writes bytes 0–1, 4–7; N3.dll n3InfoItemRemote_t::Write at RVA 0x98F4 writes opcode, affected identity, and ToBePassedOn at bytes 16–28. Retail captures independently match those writes. Packet body: Three Vector3s, two of them named and the third with no reader, which is what keeps this amber. Extracted-client ServerPosDebugInfoIIR_c has vtable 0x10162360, reader 0x100774EE, writer 0x100774BC and dispatcher 0x10077527; the reader takes twelve floats and the writer puts back the same twelve. The dispatcher resolves the message identity to a character and copies the three vectors onto it at 0x10057777 - the first to +0x224, the second to +0x230, the third to +0x23C. What the first two are for is settled by the only place that reads them back, at 0x1005ABFB, which runs every frame: it gives up at once when the vector at +0x224 is zero, and otherwise calls VisualEnvFX_t::DisplaySyncPosition - exported from DisplaySystem.dll at 0x10060E67 and taking four Vector3s - with the character's own Vehicle_t::GetGlobalPos as the first and last argument, +0x224 as the second and +0x230 as the third, substituting the client's own position for the third when +0x230 is zero. DisplaySyncPosition draws a marker at each of the four in its own colour and joins them, and does nothing at all unless bit 0x400 of the display flags is set - a debug overlay, which is what the message is called. So the first vector is the server's position for the character and the second is a second one it can send beside it. The third is copied to +0x23C and never read. That claim was first made from a linear sweep of Gamecode's text section, which is not a sound way to ask the question - a text section holds jump tables and padding, and a linear disassembler desynchronises on the first of them and stays wrong for a long stretch after. A scan that anchors on the encoded displacement instead was re-run over all three of the vector's words on 2026-09-11: + 0x23C, + 0x240 and + 0x244 are written by the character constructor at 0x1005D1F0, which zeroes a whole run of members, and by this message's own copy-back at 0x10057797, and by nothing else at all. There is no read. The caveat that remains is narrower than the old one: the scan sees the plain [register + displacement] form and would miss an access computed off a pointer taken into a local earlier, so this is still "no reader found" rather than "no reader exists" - but it is now a search that would have found one. Worth noting beside it: the overlay the first two vectors feed, VisualEnvFX_t::DisplaySyncPosition, takes four Vector3s, and the client passes the character's own position as the fourth rather than this. No capture contains one, so ServerPosDebugInfoMatchesTheLayoutTakenFromTheClient pins the layout rather than checking it against retail; before this the message had no C# at all.
