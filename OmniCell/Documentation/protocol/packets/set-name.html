Extracted-client SetNameIIR_t has vtable 0x101622F8, reader 0x10077090, writer 0x10077004 and dispatcher 0x10077207. The reader takes an int32, a byte, an int32 length and that many raw bytes, an Identity and a final int32; the writer emits the same six in the same order, so there are two independent sources for the layout. The only constructor, at 0x10077065, is reached from the message factory at 0x1000BDCD and from nowhere else, so the client never builds one of these and the reader and the dispatcher are all there is. The reader also sets the bounds: it refuses the whole message unless the length is at least 1 and below 0x20, so a name is one to thirty one bytes and carries no terminator on the wire - the NUL the reader writes at 0x10077100 goes into its own stack buffer. The dispatcher resolves the message's own identity with n3Dynel_t::GetDynel and calls 0x1005BB92 with the int32 and the string. That function is a four way switch on the int32 and each arm writes a different std::string on the dynel: 1 goes to +0x170, 2 to +0x18C, 3 to +0x154 and 4 to a heap string at +0x1A8, with anything else falling through to 0x1005BD4C, which does nothing. Two of the four are named outright by the exports that read those same members straight back - n3EngineClientAnarchy_t::N3Msg_GetFirstName returns +0x170 at 0x10018968 and N3Msg_GetLastName returns +0x18C at 0x100189A5. The constructor at 0x1005D13B initialises the three inline strings in the order +0x154, +0x170, +0x18C, which puts slot 3's string immediately in front of the first name. Slot 3 is the one Clone uses, and it is the only slot the client treats specially: the dispatcher clears bit 0x40 through two virtual calls before storing, and the store at 0x1005BCF6 walks the string replacing every '/' with an 'X' - which is what a name a person typed gets, and not what a name the server owns needs. Naming slots 3 and 4 is what is left, and the byte, the Identity and the trailing int32 with them: the reader keeps the byte as a boolean at the message's +0x38 and the Identity and int32 at +0x3C and +0x44, the writer emits all three again, and the dispatcher reads none of them. No capture contains one, so SetNameMatchesTheLayoutTakenFromTheClient pins the layout rather than checking it against retail; before this the message had no C# and no write-up at all.
