Native client proof: MessageProtocol.dll Message_t::CreateDataBlock creates bytes 2–15; Connection.dll Connection_t::Send at RVA 0x16F3 writes bytes 0–1, 4–7; N3.dll n3InfoItemRemote_t::Write at RVA 0x98F4 writes opcode, affected identity, and ToBePassedOn at bytes 16–28. Retail captures independently match those writes. Packet body: A door is a lockable item with two more fields on the end, and everything before those two is already settled by the rest of the family. Extracted-client DoorFullUpdateIIR_t has vtable 0x10167AEC and reader 0x1009FF81, and that reader calls LockableItemFullUpdateIIR_t::ReadSubClass at 0x100A0C87 for all of it and then reads a version and one int32. The version is checked against the static at 0x101C1FF8, which holds 2. Two fields the family shares are worth restating because the doors are what prove them. The identity every item message carries after the playfield is not a marker: 1000015 is the identity type of a state machine, which the client builds from stat 450, statemachine, at 0x10087B15 and again in SimpleItemFullUpdate's dispatcher at 0x100A1C31 before looking it up in the registry at 0x101C18E0. Items carry instance 0, meaning none; all 142 captured doors carry 1, because a door has states to be in. And the position gate is the instance half of the owner identity, not the type - this message had kept the type, which never showed because every captured door has both halves zero, and was corrected on 2026-09-10. The trailing int32 is the one field left. It differs between the captured copies and takes exactly 25 values across exactly 25 doors, so it identifies the door rather than describing it, and it is two int16s. The high half is the room the door stands in, counted into the room table the same playfield's PlayfieldAnarchyF carries - which is checkable, because every captured door is in the captured mission. Putting a door's world position back on the generator's grid, by dividing X by ten and doing the same for Z measured from the far edge, lands it on the cell of the room the high half names, within the half cell a door sits off centre by because it stands in a wall. It runs 1 to 22 across the building with -1 on the one door leading outside. The low half is not a second room - it is nowhere near the door - but groups doors, seven of them sharing 8 and six sharing 1, which looks like a section of the building and is not named on looking like one. The client reads the whole int32 into message + 0x78 and neither the create path at 0x1009FFF9 nor the shared dispatcher at 0x100A0BEF reads it back. The last Unknown is named and N3.dll named it: the int32 at the end is two 16 bit room indices. 0x1007F51F splits the pair the client keeps at Door_t +0x1D0 and hands each half to n3Playfield_t::GetRoom, skipping either half that reads 0xFFFF, and it only runs at all when n3Playfield_t::IsDungeon agrees; the pair also goes out whole to n3RoomMonitor_t::DoorOpened and DoorClosed at 0x1007F4C3 and 0x1007F4FD. Building a DoorFullUpdate from a door copies Door_t +0x1D0 straight into the message at +0x78, at 0x100A0101, which closes the loop. Which half is which had already been settled from the geometry, and the client agrees; what the geometry could not show is that the other half is a room too, because a door between two rooms is only ever standing in one of them.
