The two trailing record integers were traced properly on 2026-09-11 and the answer is that nothing reads them. The record is 0x30 bytes in memory and every byte of it is accounted for: an int32 playfield at + 0, an Identity at + 4, a std::string at + 0xC, and the two int32s at + 0x2C and + 0x28 - in that order, which is the order the reader at 0x1012905A takes them and the order the writer at 0x10128FFF puts them back, so the two agree and the model is not one field out. The only consumer is the GUI. GUI.dll imports N3Msg_GetGridDestinationList and calls it once, from the list builder at 0x101003D8, which walks the vector at stride 0x30 and touches + 0 - handed to N3Msg_GetPFName - the Identity at + 4, and the label at + 0xC, and nothing else. What comes back when a row is chosen is narrower still: the row object keeps the Identity and the playfield, and N3Msg_GridDestinationSelected takes a row index, that playfield and that Identity, with the cancel path at 0x100FFF4A passing -1 and an empty Identity. Neither + 0x28 nor + 0x2C reaches either. So the client stores them, writes them back if asked, and never looks at them, and no capture carries one of these messages to read a value off. That is the whole reason this packet is amber, and it is not a gap that can be closed from this build.
