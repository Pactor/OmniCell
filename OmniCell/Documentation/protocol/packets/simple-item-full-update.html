Native client proof: MessageProtocol.dll Message_t::CreateDataBlock creates bytes 2–15; Connection.dll Connection_t::Send at RVA 0x16F3 writes bytes 0–1, 4–7; N3.dll n3InfoItemRemote_t::Write at RVA 0x98F4 writes opcode, affected identity, and ToBePassedOn at bytes 16–28. Retail captures independently match those writes. Packet body: Every byte is identified. Extracted-client SimpleItemFullUpdateIIR_t vtable 0x10167D0C identifies reader 0x100A1661; its WriteSubClass is a bare return, so the client never sends this and the reader is the only source. The leading int32 is a version, compared against the static at 0x101C2160 which holds 11, and a mismatch abandons the message without reading anything else - all 747 captured copies carry 11. The reader then reads the coordinates and heading ONLY when the owner identity is empty, which is what separates an item lying in the world from one somebody is holding; 647 of the 747 are the world case, and the remaining 100 have no position on the wire at all. It is the instance half that decides it, not the type - in this message the two are always zero together and cannot be told apart, and VendingMachineFullUpdate, which is the same wire format, has 81 copies where they differ and settles it. If the quaternion fails the validity check at 0x100A15BF the client replaces it with the identity rotation rather than rejecting the packet. The two bytes after the marker are named by what the client does with them: 0x100A1B83 sign-extends the first into stat 55, inventoryid, and 0x100A1B94 sign-extends the second into stat 220, currbodylocation. The marker Identity is the shared item-message constant 1000015 with a zero instance, and the client does nothing with it whatsoever - across every method the class has, 0x100A0F9E to 0x100A1C60, the only code that touches those two object offsets is the constructor, which zeroes them, and the reader, which fills them. Nothing reads them back, so what the client makes of it is settled and only the server's reason for sending it is not.
