One of the five messages the city GUI sends, and all five are built the same way: the sender takes the city's CityAI_c, calls GetID - exported from city.dll at 0x100027E2, returning a CityID_t - and pushes that structure's +4 into the message. CityID_t opens with an Identity, read by city.dll's own identity operator at 0x100274BB, so +4 is its instance half and the int32 on the wire is which city. Nothing more of the city id travels, because the request arrives at that city's own CityAI_c and the server has the rest. These are messages the client only sends - every one of the five dispatchers does nothing but clear the pass-on flag - and no capture contains one, because catching one would need a city. This one carries a tile as well, and city.dll names both halves: CityAI_c::ClientRequestDemolish(Identity const&, TilePos_c const&) at 0x10002A40 takes the requester and the tile, which is exactly what is here once the city id has said which CityAI_c. The tile is two int32s - TilePos_c's own stream reader at city.dll 0x1001B7A3 takes one into +0 and one into +4, and its constructor is TilePos_c(int, int) - and the message reads it through that operator, imported at Gamecode 0x101553B0. A tile is how a building is named throughout the city code: the server announces a demolition as SlotPlayfieldHouseDemolishStarted(TilePos_c const&) and the client looks a house up with GetTemplateAtTilePos.
