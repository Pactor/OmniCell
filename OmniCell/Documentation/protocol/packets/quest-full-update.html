Native client proof: MessageProtocol.dll Message_t::CreateDataBlock creates bytes 2–15; Connection.dll Connection_t::Send at RVA 0x16F3 writes bytes 0–1, 4–7; N3.dll n3InfoItemRemote_t::Write at RVA 0x98F4 writes opcode, affected identity, and ToBePassedOn at bytes 16–28. Retail captures independently match those writes. Packet body: Two fields of its own, both settled, on top of a record that is not. Extracted-client QuestFullUpdateIIR_t has vtable 0x101683E8, reader 0x100ACF68, writer 0x100ACFA2 and dispatcher 0x100ACFDE. The reader hands the stream to the quest list reader at 0x100AC2BA and then takes one byte, compares it against zero and keeps the answer as a bool at the message's +0x28; the writer emits the list and that byte. The list reader is a plain X3F1 count - it divides by 0x3F1 and refuses a remainder - and then, per entry, an Identity, a 0xF8 byte quest object constructed from it at 0x100AB79A, and the rest of the record read by 0x100ABEA7. That record is the same one QuestAlternative carries, and it was walked to the last instruction on 2026-09-11 - reward box, version-gated tail and all - so what keeps this off green is no longer the shape but the handful of fields inside it that have no meaning yet. The byte is settled, and it is not what this repository called it. The dispatcher resolves the message identity, asks the character for its quest list, and then calls 0x10056CDD once per quest in the list with the byte as its second argument. That function appends the quest to the character's list and then, only when the byte is non-zero and the character carries the +0x140 flag that marks the one the player controls, raises the feedback string "Feedback_YouGotANewMission" and emits GlobalSignals_c + 0x154 with the quest's identity. So it is an announcement flag - per send, not per quest - and it was modelled as HasMore, a continuation marker, which it is not. Nothing in any shipped image subscribes to + 0x154; a signal scan finds the emit and nothing else. Retail settles which way it sets the byte, and it agrees. The capture taken on 2026-09-11 of a character made from scratch carries four copies, each with one quest. The quest "Kill a Leet" appears in two of them: in the first zone session, at the point it was given, with the byte set; and again near the start of the next zone session, the window refresh after zoning, with the byte clear. The other two are quests given during that second session and both carry it set. So the byte marks the send that gives the quest and is clear on a refresh, which is what this server now does - it used to set it on every send, including the refresh on entering a playfield. All four round trip byte for byte. Two of QuestInfo's unnamed int32s are a time limit, found on 2026-09-11. Across all 193 captured quest records the pair holds the same value every time - 185 pairs of zero, four of 2880 and four of 7200 - and two independent int32s do not do that. 2880 seconds is forty-eight minutes and 7200 is two hours, which are mission time limits and not much else; zero is a quest without one. Why there are two is not settled: a limit beside a remaining time would be equal at the moment a mission is granted, and every captured record is a zone-in snapshot rather than a mid-mission one, so the captures cannot separate them. The client's own N3Msg_QuestRemainingTime reads neither - it walks the quest's action list and takes a deadline off QuestAction_t + 0x5C, a different field in a different record, which is a lead for the action record rather than this one. Some of the client's own member map came out of the same trace and is worth carrying even though it does not name a field on its own. The per-quest reader at Gamecode 0x100ABEA7 takes an int32 version and abandons the record unless it is 7 to 15; then two int32s into one stack local, which is what makes them unread; then the flags into Quest_t + 0xA4, the short string into + 8 and the long string into + 0x88, all three matching the exported accessors. Then an Identity into + 0x38 - the quest giver - a reward box through the reader at 0x100870A8, which has a version gate of its own at 3 to 6, an Identity into + 0x40, and int32s into + 0x48, + 0x70 and + 0x74 before the action list at + 0x28. N3Msg_GetQuestIcon returns + 0x48, and walking the reward box settled which member that is. The box, at Quest_t + 0x34 and read by 0x100870A8, has a version of its own gated 3 to 6 and most of its body is conditional on it: always the cash into box + 0, an int32 into a discarded stack local, the experience into box + 4, two X3F1 Identity lists and an item list at box + 0x1C; then three more int32s at box + 8, + 0x14 and + 0x18 only from version 4, two more at box + 0xC and + 0x10 only from version 5, and a whole GameData::ACGItem_t at box + 0x28 only from version 6, read through the client's own stream operator for that type. N3Msg_QuestGetCashReward and N3Msg_QuestGetXPReward confirm the first two - both resolve the quest, take + 0x34 and then + 0 and + 4 - and N3Msg_GetItemRewardList takes box + 0x28 and compares it against GameData::ACGItem_t::zero. So the box swallows nine of the model's members, 8 through 23, and with that counted the rest falls out: the Identity after it at + 0x40 is Owner, and the int32 after that at + 0x48 is MissionIconId, which is therefore the quest icon by the client's own accessor rather than by the shape of its values. The two seconds fields land at + 0x70 and + 0x74, and the action list at + 0x28 follows them. The naive alignment, before the box was walked, put the icon three members earlier on a field that is zero in all 193 records - which would have meant a client that never draws one. That is what the off-by-one was. One thing this exposes rather than fixes: the model flattens the box's version-gated tail as unconditional quest fields. Every captured record carries box version 6, so all four branches are taken and the flattened read is byte-exact, but a server sending version 3 would put none of members 15 to 23 on the wire and the model would read past the end. Members 20 to 23 are also not four loose int32s - they are one ACGItem_t, the same record the model already has an AcgItem class for. The action record was mapped the same way on 2026-09-11 and gives up two more names. Each action is 0x8C bytes, read by 0x100ACBA0: an int32 version, then five Identities, four floats, an Identity, four more floats, an Identity, two int32s, an Identity, and a GameData::WorldPos_c. The first of the two int32s, at QuestAction_t + 0x5C, is a deadline. N3Msg_QuestRemainingTime - exported from Interfaces.dll at 0x1000A8AC - is the whole argument: it walks the quest's action list, takes each action's + 0x5C, skips the zeros and returns the difference against the server clock, and a deadline is the only thing you subtract a clock from. The values agree: eight of the 193 captured records carry a non-zero one and they decode as 2026-09-13 01:09 and 01:26 and 2026-09-16 12:00, 12:04 and 12:05, which is one day and five days after the captures they arrived in. The other 185 are zero. Its old name in the model was UnknownHash15, which is what a timestamp looks like if you do not check the date. The tail is one record rather than six loose fields: the reader hands + 0x6C straight to the client's own stream operator for GameData::WorldPos_c, and N3Msg_GetQuestWorldPos at 0x1001ABC9 reaches the quest's action list, takes the first action, adds 0x6C and returns the Identity at + 0 with vectors from + 8 and + 0x14. That is what an earlier note meant when it said GetQuestWorldPos reaches the marker through the action list rather than off the quest - the marker is this field. One loose end from that trace is closed. The WorldPos_c is 32 bytes in memory and 28 on the wire, which looked like the model reading four bytes short in a list record - the kind of mistake that shifts every element after the first and that a byte-exact round trip would not catch on a one-element list. It is not one. GameData.dll's reader at 0x1000CA52 reads an Identity, two int32s and three floats - 28 bytes - and then builds the second Vector3 rather than reading it: each int32 goes through fild into components 0 and 2 and an fldz goes into component 1, so the derived position has no height. N3Msg_GetQuestWorldPos hands its caller both vectors, the read one and the derived one. The three floats are the marker and the captures say so independently: X runs 3431 to 3621 and Z 797 to 880, the same magnitude as the character coordinates in the SimpleCharFullUpdates of the same sessions, and Y is zero in 192 of 193. The int pair is not the same position in the same units - 100000 with 100000 in 173 records, which reads as a sentinel, and otherwise 41975 with 45030 and 34495 with 29814. The reward box stopped being flattened on 2026-09-11. Its version-gated tail - three int32s from version 4, two more from version 5, an ACGItem_t from version 6 - was modelled as nine unconditional members, which is byte-exact on every captured record because every captured record is version 6, and would read past the end of one that was not. The gate at 0x10087117 refuses anything outside 3 to 6, so the conditions can be written as exact value lists rather than comparisons and mean the same thing. The four loose int32s at the end became the one ACGItem_t they always were. All 241 records still round trip byte for byte. Two of the box's fields have outgrown their own notes. Both were recorded as zero in all 193 records; the corpus is 241 and 73 of them carry values. Box + 0xC holds a second four character code - 925D, 5UFZ, XX76, N6MO, 58YD, IGMR, E7AC, 12Y8, MMSU, L5H7, 8YIR, QSOR, 3JRQ, DIRM, MSRE, YNRL and IWQB, every one of the seventeen printable, which is the shape of a mission key - and box + 0x10 holds 1, 2, 3, 4, 5, 7, 9, 10, 11, 39, 212 or 250 on the same 73 records. The obvious route was tried on 2026-09-12 and closed: SimpleCharFullUpdate's weapon pair carries four character codes too and every one of those is in the resource database, beside the Equip_ record it belongs to. None of these seventeen is. That is not a gap in the search but the answer to a different question - a mission the content generator built has no authored record to be named from, so a key for one can only have been made when the mission was, and it will not be found by reading the client. They move together. Which kind of quest carries them is not settled: splitting the captures by quest name does not separate them, but a packet carries up to three quests and that test could not say which record inside a packet the code belonged to. And one thing is now ruled out rather than merely unclaimed - box + 8 and box + 0x14 are consecutive on the wire and were read as the two halves of an Identity, but the reader puts them eight bytes apart with two other fields between, and an Identity is read as a unit. The tail was walked instruction by instruction on 2026-09-11, and the last ten members of the quest record turn out to be version-gated exactly as the reward box is. From 0x100AC08C the reader is a staircase - jge against 8, then 9, 10, 11, 12, 13, 14 and 15, each else arm zeroing its member instead of reading it - and this model read all ten unconditionally. Every captured record is version 15, so every arm is taken and all 241 are byte exact; a server sending 14 would have left four bytes on the wire, 13 a whole list, and so on down. The gate at 0x100ABECE refuses any version outside 7 to 15, so the value lists that express it are exact and not an approximation. One arm gives the pattern away: below version 8 the client does not zero that member, it writes 6 - and our own server already sends 6 there, from a constant named for the field, which is the client's default arrived at independently. Three shapes in the middle of the tail came out of the same walk. The two int32 lists are plain int32 counts rather than X3F1, and every element is masked with 0x07FFFFFF before the client keeps it, so the top five bits of each are on the wire and discarded. The character info list is an int32 count and then, per entry, an Identity, an int32 length and that many bytes - which the client reads into a stack buffer and does nothing with. And a warning for the next person: 0x100458BB, which appears all through this tail, is not a stream reader. It takes a member vector and a value and appends, so a trace that reads the call listing rather than the instructions will count list readers that are not there. That mistake was made first and corrected here.
