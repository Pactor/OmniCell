Native client proof: MessageProtocol.dll Message_t::CreateDataBlock creates bytes 2–15; Connection.dll Connection_t::Send at RVA 0x16F3 writes bytes 0–1, 4–7; N3.dll n3InfoItemRemote_t::Write at RVA 0x98F4 writes opcode, affected identity, and ToBePassedOn at bytes 16–28. Retail captures independently match those writes. Packet body: Every byte of this message is identified, and the last three came from a reader inside Gamecode that nobody had looked for. Extracted-client RaidIIR_c has vtable 0x10167F2C, reader 0x100A3B2E, writer 0x100A3B63 and dispatcher 0x100A40C0. The reader takes an int16 and widens it; the writer narrows the same field back to an int16, so two bytes is what travels even though the client holds four. Only the value 1 carries a body, and then it is read by 0x1005731B: an int32 that must be 1 or the rest is skipped - a version - then a plain int32 count and that many twenty byte records, each two Identities and an int32, read by 0x10057277. The dispatcher tells the two values apart. Zero resolves the message identity to a character, clears the team subsystem's +0x38 - the same member N3Msg_GetRaidTeamIndex reads - raises the feedback string "Feedback_RaidCreated" and emits GlobalSignals_c + 0x13C, which GUI.dll connects at 0x10103609 to the handler at 0x10102D5E that greys the raid window's create button out. So zero is the raid being formed. One walks the list into +0xB8 of the object the character's world handler returns. That is where this stopped before: no export reaches +0xB8, Interfaces.dll has N3Msg_RequestRaidLocks to ask for the list and nothing at all to read it back, and the consumer was written up as a GUI signal that could not be followed. It is not a GUI signal. The same dispatcher calls 0x100430C2 two instructions later, and that is the reader: it walks +0xB8 at stride 0x14 and prints a line per entry under the heading "Raid locks:". The line is built by the append chain at 0x1004318F as name, then "(", the first Identity's instance, "): ", the second Identity's instance, " - ", and then hours, minutes and seconds. The name settles the first Identity outright - it is the return of the lookup at 0x10036982, and that address is the entire body of the export n3EngineClientAnarchy_t::N3Msg_GetPFName(unsigned int) at 0x10016AE6, so the first Identity is a playfield and "Unknown" is what the client prints when the table has no entry for it. The second is printed as a bare number beside it and nothing resolves it further. The int32 is settled by the arithmetic around it at 0x10043142: the client subtracts its own current time from it and divides the difference by 0xE10 and then by 0x3C to get the hours, minutes and seconds it prints, which makes it an absolute time rather than a duration. No capture contains one, so RaidCreatedCarriesNothingAfterTheKind and RaidLocksMatchesTheLayoutTakenFromTheClient pin the layout rather than checking it against retail; before this the message had no C# at all.
