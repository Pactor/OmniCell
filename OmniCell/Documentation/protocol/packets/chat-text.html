Native client proof: MessageProtocol.dll Message_t::CreateDataBlock creates bytes 2–15; Connection.dll Connection_t::Send at RVA 0x16F3 writes bytes 0–1, 4–7; N3.dll n3InfoItemRemote_t::Write at RVA 0x98F4 writes opcode, affected identity, and ToBePassedOn at bytes 16–28. Retail captures independently match those writes. Packet body: Four fields, and three of them were called Unknown until the trail was followed into a second module. Extracted-client ChatTextIIR_t has vtable 0x1015E0BC, reader 0x10038930 and writer 0x1003881E, and they agree: a two byte counted string, a byte, a byte, an int32. The reader refuses a second byte above 1, and the dispatcher at 0x1003889D is one branch on exactly that - zero hands the line to the engine's chat text signal, one builds a colour out of three floats the client keeps for the purpose and calls 0x1001137A, which is the floating on-screen message and has neither a window nor a colour. The signal is where the other two are named. It is the same one the client's own debug-to-chat commands use, and the arguments land in the same order: the int32 first, the text second, the first byte third. GUI.dll subscribes at 0x10083E7B. The subscriber treats the first argument as a window id - it looks the value up directly below 0x40000000 and by name above it - and then calls that window's AddLine with the text and the byte. AddLine at 0x1009BAD0 looks the byte up in the colour table at 0x10268D38 and wraps the line in a font tag, or leaves the line alone when the value is zero. Entry 16 of that table is CCYellow, and the one captured copy is a system announcement carrying 16. The window is the same routing value OrgClient carries in the other direction, in the same argument position of the same signal.
