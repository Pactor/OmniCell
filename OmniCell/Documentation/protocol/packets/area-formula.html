Retail captures independently match those writes. Packet body: Green on 2026-09-11, after the whole chain was walked again rather than taken on the note that used to stand here. Every transmitted byte is identified. AreaFormulaIIR_t has vtable 0x10161D2C, reader 0x100721DC, writer 0x10072142 and dispatcher 0x1007212D.

The reader is three calls and nothing else: 0x1002BA77 for an X3F1 counted Identity list into the message + 0x24, the int32 operator into + 0x20, and the shared Identity reader 0x1013D2F9 into + 0x18. No version, no conditional, no fourth field.

The dispatcher hands all three straight to 0x100A9A99 - the source Identity, the list and the int32 - and that walks the list, resolves each entry with n3Dynel_t::GetDynel, casts it, and for each one that resolves calls 0x10051C98 with the int32 and the source. 0x10051C98 opens by passing the int32 to 0x100A4B10 and giving up if it comes back null, and 0x100A4B10 builds an Identity of type 0xFDE85 with the int32 as its instance - the constant is written at 0x100A4B78 - and asks ResourceDatabase_t::GetBinaryStream for it. So the int32 is a resource id, loaded out of the resource database, applied to every listed target from the trailing source character.

The extracted item-name database identifies both captured instances as nano formulas: 158506 is Shockball and 158523 is Brief Poison Fog. Across 91 retained copies the target list varies, the formula identifies the applied area nano, and the trailing Identity is the constant casting character - the one that also owns the Stat, CharDCMove, CastNanoSpell, CharacterAction and WeaponItemFullUpdate messages of the same sessions. The server value rule is therefore: list every affected character Identity, select the nano formula resource id being applied, and supply the caster Identity.
