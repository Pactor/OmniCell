Native client proof: MessageProtocol.dll Message_t::CreateDataBlock creates bytes 2–15; Connection.dll Connection_t::Send at RVA 0x16F3 writes bytes 0–1, 4–7; N3.dll n3InfoItemRemote_t::Write at RVA 0x98F4 writes opcode, affected identity, and ToBePassedOn at bytes 16–28. Retail captures independently match those writes. Packet body: A slash command on its way to the server. The client calls it Fanatic::FanaticIIR_t, in Fanatic.dll: vtable 0x100031C0, dispatcher 0x10001109, reader 0x10001214 and writer 0x10001112. The dispatcher only clears ToBePassedOn, so this is outbound. The reader and writer agree on an int32, an Identity, an int32 byte count and exactly that many command bytes, with no terminator; the reader refuses a count above 0x2710 or beyond the remaining stream. Fanatic.dll exports the sender as Fanatic::ClientInterface_c::Command(int, Identity const&, std::string const&). GUI.dll is its only importer and has exactly four calls, at 0x100B3737, 0x100B383E, 0x100B3A46 and 0x100B3FD1. The destination comes from the local character object returned by 0x1001B714. The command string is built from the typed buffer plus one, dropping the slash. The first int is the originating chat-window id. Three calls take it from the command context at +0x1EC; the fourth accepts it as a Variant and converts it with Variant::AsInt32. That same GUI member and meaning are independently exposed by OrgClient: all N3Msg_TextCommand call sites pass the chat-window object's +0x1EC, and debug command replies dispatch the same leading integer to chat text listeners so the answer returns to the window that requested it; commands raised by a dialog pass zero. The earlier /get, /getfull and /set attribution was discarded: An earlier scan had mistaken a branch inside an unrelated signal notifier for a shared command handler. Green on 2026-09-11, after the reader and writer were walked rather than taken on the summary above. Both are total and both agree. The reader takes an int32 into + 0x18, an Identity into + 0x1C through 0x10001C00 - falling back to n3InfoItem_t::GetDestinationID only when both halves arrive zero, which is the behaviour this page already described - an int32 length, refused at 0x10001269 if it is longer than the stream has left and at 0x1000126E if it is above 0x2710, and then exactly that many bytes into the string at + 0x24 with no terminator. The writer emits the same four in the same order. There is no fifth field and no conditional, and each of the four is named with its own evidence, so there is nothing left in it to identify.
