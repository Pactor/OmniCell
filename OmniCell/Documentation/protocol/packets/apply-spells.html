Native client proof: MessageProtocol.dll Message_t::CreateDataBlock creates bytes 2–15; Connection.dll Connection_t::Send at RVA 0x16F3 writes bytes 0–1, 4–7; N3.dll n3InfoItemRemote_t::Write at RVA 0x98F4 writes opcode, affected identity, and ToBePassedOn at bytes 16–28. Retail captures independently match those writes. Packet body: Three fields, and both of the things this entry used to say about them were wrong. Extracted-client ApplySpellsIIR_t vtable 0x10171684 identifies reader 0x10128EA9, writer 0x10128EEF and dispatcher 0x10128E45, and the reader takes the list, then an Identity, then one byte. The list is not an array of spell ids. 0x100A71AE is the same X3F1 counted reader SpellList and CorpseFullUpdate use, and each element it allocates is 0xD8 bytes with its own pair of vtables - a GameData SpellData_t, the whole record, tail included. The identity is a character: the dispatcher resolves it in the playfield and casts the result from n3Dynel_t to SimpleChar_t before doing anything with it. The byte was recorded as an unresolved boolean, and the reason it looked unresolvable is that the dispatcher inverts it at 0x10128E8A before passing it on, so the dispatcher alone says the sense is backwards from something without saying what. Two calls further on it settles. The inverted value is argument three of SimpleChar_t's spell routine at 0x100026D0, which at 0x10002823 makes it bit 0 of each applied effect's flag word; and an effect whose bit 0 is set subtracts its amount from the target's stat where an effect without it adds - 0x100A4F6C is one branch around a sub and an add, nothing else. Effects that act once rather than modify a stat check the same bit and do nothing when it is set, at 0x100A52D9. So the byte says which way this message goes: 1 puts the listed effects on the character, 0 takes them off. No capture carries this message, so the layout is the client's reader and writer and nothing else, and the test says so.
