Native client proof: MessageProtocol.dll Message_t::CreateDataBlock creates bytes 2–15; Connection.dll Connection_t::Send at RVA 0x16F3 writes bytes 0–1, 4–7; N3.dll n3InfoItemRemote_t::Write at RVA 0x98F4 writes opcode, affected identity, and ToBePassedOn at bytes 16–28. Retail captures independently match those writes. Packet body: A corpse is a chest with a tail, and most of this message was already understood under other names. CorpseFullUpdateIIR_t::ReadSubClass at Gamecode.dll 0x1009FA4C reads an int32, refuses anything but 8, then calls ChestFullUpdateIIR_t::ReadSubClass for the whole of the next stretch - which is itself LockableItemFullUpdate on top of SimpleItemFullUpdate - and only then reads a tail of its own. So ten fields that were numbered Unknowns are the item family: an item version of 11, the identity of whoever is holding the corpse (nobody, which is what puts the position on the wire), the playfield, the state machine identity, the packed inventory id and body location, the stat list, the name, the lockable version of 2, lockdifficulty 50, the keyholder list and the chest version of 3. The keyholder list was modelled as int32s where the client reads Identities; every captured copy is empty, so the two are the same four bytes of count. One thing the corpse settles for the whole family: its state machine identity type is a plain zero, where every item carries 1000015. That confirms the 1000015 is a property of those items rather than of the format. The tail is four things and they are read but not yet named here. A counted list of GameData SpellData_t records - the same nano effect record SpellList carries, read by the same function at 0x100A71AE - then an Identity, which is the character the corpse used to be, then a vector of ClothData_t, which is the same cloth list AppearanceUpdate carries, and finally an int32 that when non-zero brings a vector of TextureData_t after it. The first of those is now read as the record it is, by the same code SpellList and ApplySpells use - the three were reading the same format in three places, and the corpse was reading it flat. The cloth and mesh entries are named too, and from an unexpected direction: both end up in a GameData TextureData_t, and VisualCATMesh_t::SetCATTextures in DisplaySystem.dll draws the first of its three int32s at the layer its caller names with the third as the alpha mode and the second at layer 3 with none. So the trailing pair on a cloth entry is an overlay texture and a blend mode, and the two ints beside a mesh name are the same two. Every byte of this message is identified.
