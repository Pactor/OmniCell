Extracted-client ScriptIIR_t has vtable 0x1017231C, reader 0x101308EE, writer 0x10130852 and dispatcher 0x10130A1B. The reader and the writer emit the same ten fields in the same order, so there are two independent sources for the layout: three int32s, a counted string, three int32s, a counted string and two int32s. Both strings go through the shared helper at 0x10038AF8, which takes an int16 length through BinaryStream's 0x101540D8 and then the characters with no terminator; its writer at 0x10038AB3 clamps the length to 0xFFFF and emits an int16. The dispatcher builds a string out of the first one and hands it to FXS_t::ExecuteScript(char const*, FXS_Object_t*), imported from FXS.dll, and files the object that comes back in a map at 0x102EACA8 keyed by the first int32. FXS is the client's effect scripting system, so this message is the server starting, superceding and stopping visual effects. The third int32 is a five way command and nothing else reaches a branch: 0 runs the script and files it; 2 does that and then supercedes; 1 supercedes without running anything and, when nothing is filed under the id, tells the playfield to drop the named script; 3 hands the playfield the script under a name instead; 4 runs it subject to range. Anything else falls to 0x10130BE9 and does nothing at all. "Supercede" is the client's own word rather than a reading of ours: the branch at 0x10130CF1 looks the second int32 up in the same map, calls FXS_ObjectClass_t::GetVariablePointer with the literal "SupercedeTime", takes the object's child named "Life" through GetChild on the hash of that string, reads that child's "StartTime" and "LifeTime", and when more than SupercedeTime has elapsed writes the child's +8 back to now minus SupercedeTime - back-dating the effect so it jumps past that point. Three of the numbers are named by the clock arithmetic that runs before the switch for every command. The client takes its own time from 0x1000B1BF + 0xB4, subtracts the third-from-last int32, keeps the smallest difference it has ever seen in the static at 0x102EACA4 and adds that to the first of the three; keeping the least-delayed sample is how you turn a server clock reading into a client one, which makes the subtrahend the server's clock and the other two a time and a length in server terms. Both then go into the script text, which is an LDB format template: ldb.dll's LDBformat takes the text, Feed takes the duration and then the corrected start, and Dump produces what ExecuteScript runs. Command 3 uses the same two the other way round - 0x10130C96 computes duration minus now plus start, which is the time the effect has left, and 0x10122DC1 hands that to the playfield along with the script and LDBface::ElfHash of the second string; command 1 uses the same hash at 0x10130E37 to take it away again. The last two int32s belong to command 4 alone: 0x10130B75 subtracts them from the first and third components of the player's own Vehicle_t::GetGlobalPos, each truncated to an integer, squares and sums, and runs the script outright when the result is at or below 0x9C40 - two hundred units squared. Beyond that it divides 0x2625A00 by the squared distance and compares against a millisecond counter modulo 1000, so distant effects thin out rather than stop. No capture contains one, so ScriptMatchesTheLayoutTakenFromTheClient pins the layout rather than checking it against retail; an entry was already here, with six of the ten named, and two of its readings needed correcting: the fifth and sixth int32s are a start time and a length rather than an accumulated total and a count, and the range check in command 4 measures from the player's own position through GetClientControlDynel, not from the message's identity.
